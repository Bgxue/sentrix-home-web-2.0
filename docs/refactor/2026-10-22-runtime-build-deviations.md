# 运行配置、build与硬件核验偏差说明

基线7d46891，开发分支codex/photobench-runtime-build-fix。导入rm002副本保留，不整包合并，尤其不移植硬编码路径及宽泛pkill脚本。

本轮扩大原“仅修指标”为用户已授权的配置闭环、build/reuse/resume、名称、HTTP稳健性、长导入可见性和Mac预算。保留同步导入契约，不引入任务队列；在飞导入的细粒度取消仍不支持，取消和替换须确认工作线程退出。

硬件能力与可运行性分开：NX系统CUDA12.6；此前Python3.11环境中的ORT1.31依赖CUDA13动态库，但10月22日实时发现磁盘原`.venv`已被换成不完整的Python3.10环境（来源未确认），运行中旧进程仍3.11，因此发布前必须独立恢复并验证产品环境；PyTorch实际内核须独立验证，不能仅凭available_providers或架构列表认定加速成功。显式CPU是合法部署，并不等于CUDA修复。AGX侧车Python3.10不可替代产品要求的Python≥3.11。优先独立候选环境，不改驱动/JetPack/系统CUDA，不覆盖活跃venv；若所需大改超出边界则保留CPU并报告证据。

生产遥测仍允许不可用并给原因；严格3秒门槛留在独立验收，不以缺遥测直接中止通用产品。旧run原文、旧制品和已有证据保全，不改标新SHA。人工owner审核与一分钟回滚实测未完成前不宣称通过。

输入初始化失败必须保存真实failed终态，未知QA数量/输入哈希保留null，不发产品请求。未知题集在创建阶段拒绝。build独立验收分母为0且评分不适用，但仍检查导入/处理核心内存覆盖。


13时续验发现NX在查看实时详情时读侧内存压力与采样停滞，旧轮不满足3秒门槛；Mac reuse也记录3.09秒缺口，均保留为未通过的遥测证据。
已确定并复现的缺陷是轮询effect依赖调用方每次渲染重建的loader，绕过既定2秒间隔；并发详情还会各自解析完整采样，造成读侧内存倍增。
修复属于前端轮询生命周期和application读侧并发编排，不修改采集公式或产品Agent，不增加新端口/env/API字段。
同run仅合并在途投影，绝不以缓存活跃run旧值掩盖停滞；失败后清理并继续传播原异常。
由于读侧负载已经影响真实采样，修复固定后扩大四机full及NX/Mac build→reuse验证，不使用旧轮证明新负载行为。
