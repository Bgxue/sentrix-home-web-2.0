# 2026-10-15 QA 修复：与 1.0 的偏离登记

依据 `docs/refactor/2026-10-15-qa-fixes-implementation-plan.md`。
**这份文档只登记「2.0 故意不照 1.0 做」的地方**；逐项实施内容与验收见计划书。

分析对象是 `20261010-161414-album3-max-video10-qwen35-q4km-ef48ac`（487 题、跑完
332 题后被取消）。对照基准是 1.0 同一题集同模型的 `20261011-021159-…-c76fab`。

## D1 · `viewer_escape` 的裸词 `他人`：收紧（§T9a）

| | 1.0 | 2.0 |
|---|---|---|
| 正则 | `别的?相册\|他人\|别的?人[的]?(?:相册\|照片\|隐私)\|其他用户`（`final_guard.py:174`） | `别的?相册\|他人[的]?(?:相册\|照片\|隐私\|内容\|信息)\|别的?人[的]?(?:相册\|照片\|隐私)\|其他用户` |
| 「与他人一起拍的合影」 | **命中 → 硬拦** | 不命中 |
| 「我还能看到他人的相册」 | 命中 | 命中 |

**理由（有实测）**：2026-10-10 那轮有 5 道题被 `viewer_escape` 硬拦，问题原文是
「我想找带强子第一次近距离看活海星和鲎的那次参观照片」这类——相册里全是家人，
「与他人」是日常说法。**硬拦不重试**（`HARD_GUARD_CODES`，1.0 `runtime.py:2784-2791`
的语义），一次误伤就是一道题归零（那 5 题均分 0.0）。

2.0 此前已为这条规则做过一次改进（`run_turn.py:899` 附近：把被打回的原文放进
`evidence`），但那只让误伤**可诊断**，误伤本身没消。这次动的是正则。

**代价**：`他人照片`（不带「的」）这一类表达不再命中。判断是：真正的越权回答会
说清对象（「他人的相册 / 隐私 / 照片」），而「他人照片」作为定语出现在正常叙述里的
概率远高于前者。

## D2 · `max_page_calls = 2`：保留（§T9b）

| | 1.0 | 2.0 |
|---|---|---|
| 翻页上限 | **没有这一项**（`ProfileConfig` 里不存在） | `max_page_calls = 2`（`profile.py:65`） |

**这是 2.0 新增的设计**，按「不新增 1.0 没有的设计」本该回退。**决定保留**，理由：

1. 1.0 不需要它，是因为 **1.0 的 `search_memories` 一次返回 18 张**（`runtime.py:1930`
   注释），而 2.0 是 `MAX_SEARCH_LIMIT = 12` + `PAGE_SIZE = 6` → **最多两页**。
   2.0 的「翻页需求」结构上更弱，越界页也更常见。
2. 实测 2026-10-10 那轮 43 次「翻页额度已经用完」被拒——**删掉上限不会让模型停止翻页**，
   只会让它继续翻、同样烧掉模型步（`tool_policy.py` 的额度判据排在 `can_call_tool()`
   之前，被拒的那次也计入 `tool_round_trips`）。
3. 它有一条跨层不变量钉着（`test_assistant_task_state.py:274`：
   `max_page_calls >= ceil(MAX_SEARCH_LIMIT / PAGE_SIZE)`）——即「额度必须够翻完整个
   结果集」，这正是它想要的性质。

**代价**：模型仍会尝试第 3 页并被拒一次。这条留给提示词解决（
`domain/assistant/tools.py:124-139` 已有「翻到没有内容的页说明已经到底」的引导），
不靠放宽额度。

## D3 · `completed` 口径：修正（1.0 同错）

| | 1.0（`benchmark_orchestrator.py:7286`） | 2.0 现在 |
|---|---|---|
| 判据 | `judge_status in {completed, failed, skipped}` | `execution_status == "completed"` |

**这不是 2.0 抄错，是 1.0 的固有缺陷**：取消掉的题在这两版里都被标成
`judge_status="skipped"`，于是「取消的 run」在列表页显示 `487/487 完成`。
实测 1.0 自己的 `20260918-203454-…`（cancelled）同样显示 1167/1167 而实际完成 0 题。

**为什么 2.0 要修而 1.0 不用**：1.0 极少遇到取消（那条路是人工中断），2.0 两轮里
遇到两次（10-08、10-10），且 2.0 的 UI 把这一格直接摆在 run 列表上。

## D4 · `/health` 增加嵌入器档位（1.0 无对应）

1.0 的 `/health` 只回答「进程与数据库」，2.0 现在多一格 `embeddings`，
且嵌入器不可用时整体回 `degraded`。

**理由**：2026-10-10 那轮 WeMM 侧车中途消失，354/370 次检索静默降级成
`backend=none`，而 `/health` 一路回 `ok`——整轮数据作废却没有任何一处报错。
**1.0 挡不住这个问题**（它的守卫打的是模型端点），所以这是 2.0 的一次主动加固，
不是移植。

## D5 · resume 不重试「真正失败」的题（与 1.0 同）

`resume` 只续跑 `execution_status in {scheduled, running}` 的题，其余（含 `failed`）
视为已完成——**逐条照 1.0 `:3414-3417`**。

配套改动：取消时排队中的题改标 `scheduled` 而不是 `failed`（`service.py` 的
`except RunCancelledError` 分支）。**没有这一条，resume 会把这 155 题当成「已跑完」而
永久跳过**——那正是「取消一次只能整轮重跑」的成因。

## D6 · 收尾绝不用固定文案（T1 的第二段）

**根本要求（用户 2026-10-15）：代码不替模型说话。**

| | 1.0 | 2.0 修复前 | 2.0 现在 |
|---|---|---|---|
| 模型已产出答案、重答失败 | 放行该版（D12，`runtime.py:2415-2419`） | **固定文案顶掉它** | 放行该版 |
| 模型一个字都没说过 | `_force_final_once`（`:1590-1623`）换一次纯 final | 固定文案 | 同样换一次，仍失败才用固定文案 |
| **安全硬拦（`GUARD_BLOCKED`）** | 固定文案 | 固定文案 | **固定文案**（不放行） |

三层实现在 `_Session.last_answer` + `_stop` + `_force_final_once`。

**那条安全界线值得写下来**——两层门禁的分工不是「严格程度」的差别，是**判的东西不同**：

- **L2（忠实性）判「说没说谎」**：打回一次（`judged` 闩保证只打回一次），模型没改好
  就**放行原话**——它至多不准确，而用户要的是一句人话而不是一句模板；
- **L1 硬拦判「能不能说」**：`internal_id_leak` / `viewer_escape` / `write_not_allowed`
  那一版答案**本身就是危害**，放行等于让掉边界，所以照旧走确定性兜底。

实测证据：这条界线是被既有门禁抓出来的——第一版实现让
`test_a_leaked_internal_identifier_is_never_delivered` 变红（它会放行泄漏
`asset_9f3a21b7c4` 的原文）。

## D7 · 回答质量：提示词加「禁止清单 + 心态约束」（2026-10-16）

逐题审查 2026-10-15 那轮 487 题后做的改动。**同一模型（qwen35-q4km）下，2.0 与 1.0
的回答质量差距全部出在提示词与结构上**：

| | 1.0 基准 | 2.0（修复前） |
|---|---|---|
| `photo_N` handle 写进回答 | **0%** | **42.7%**（满分题里 28%） |
| 工具名 / 工具调用 JSON 进正文 | 0.2% | **13.8%**（含 10 题裸 `<tool_call>` XML 当回答） |
| markdown 加粗 / 列表 | 2.5% | **64.9%** |
| 回答平均长度 | **95 字** | **277 字** |

**根因**：1.0 的 `BASE_SYSTEM_PROMPT`（`jit_prompt.py:17`）有三条 2.0 没有的约束——
① 「不要输出 markdown 代码块或解释」；② 「**内部检索词汇……不得原样出现在回答里**，
用自然语言转译」；③ 不确定性分级表述。**2.0 迁移到原生 tool_calls 时只保留了参数契约，
丢了这三条。**

**一处刻意的做法**：字段名（`final_answer` / `selected_image_handles`）在提示词里
**照提**——模型必须知道往哪填，1.0 也照提。禁止的是它们**出现在给用户的回答正文里**。
这比"把字段藏起来"更接近问题的实质：**要区分的是「内部用语」与「用户可见文本」，
不是「让模型看不见」**。

**未做**：没有加出口清洗（用户 2026-10-16 裁决）。理由是那会把真问题盖住——
清洗能让回答看起来干净，但模型为什么会写出 `photo_1` 这件事会失去证据。

## D8 · 交付链路的三处修复 + 一处可观测性缺口（2026-10-16）

| 项 | 1.0 | 2.0 修复前 | 2.0 现在 |
|---|---|---|---|
| 空数组 `[]` | 合法（交付为空） | **`missing_handle` 错误码** | 合法 |
| 去重 / 上限 6 | 有（`runtime.py:239-251`） | 无（只在 schema 声明 `maxItems`） | 有 |
| 交付物带类型 | 无 | 无 | `Attachment.media_type` |
| 终态动作的轨迹 | — | **arguments/result 被投影成 `{}`** | 完整记录 |

**1.0 有、2.0 丢掉的一条结构性约束（未修，记录在案）**：1.0 的合法交付集是
**`task.result_preview`**——**模型当前实际预览到的那几个 handle**；2.0 的 `deliver`
按**整个结果集**解引用。也就是「只能交付你看过的」这条约束在 2.0 消失了。
实测 $album3v4-403$ 交付的 `photo_7/8/9/10` 就是它没在当前页看过的。
**这条是否要补，留给后续裁决**——它可能正是「91 题交付了一张都没对上、其中 49 题 GT
就在候选里」的一个来源。

**另外两条调查结论，不修但要知道**：

1. **「说『以下是照片：』却没交付」在本轮不成立**——那样的 2 题都交付成功了，那个尾巴
   是设计模式（照片走 attachments 单独渲染）。当初的定量扫描用正则误判了它。
2. **「交付了视频却说没找到视频」是评测口径**——模型交付的是视频的**抽帧**
   （`kf_0001.jpg`，本身就是 `media_type='image'` 的普通资产），说的是实话；
   PhotoBench 的 `resolve_predicted_media`（`execution.py:230-247`）把关键帧投影回源视频，
   才在指标里合成出"交付了视频"。这条回落规则 1.0 也有、要保留。
